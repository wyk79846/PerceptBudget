# M3关键位置短暂等待

## 同阶段刷新去重（2026-10-31）

新增独立实验开关`--phase-refresh`，仅M3。前两版只减少暂停，仍允许同一次抓取阶段内不断重新预测。现在事件触发的Full提交后，若触发位置属于旧chunk中已经观察到恢复峰的阶段，记录旧阶段的固定起止位置；该阶段后续的同向夹爪、减速、转向事件不再触发刷新。相反方向夹爪事件继续有效。缓冲耗尽、RTC前缀限制与其他硬约束仍可触发Full，不是锁死动作队列。没有明确恢复峰则不建立整段豁免。

它只在一次事件响应完成后生效，不自动把所有buffer刷新都视为覆盖未来抓取。原预测target50响应提交后，历史回放中51步的slowdown52被过滤，下一未覆盖事件为gripper_open73。不会声称消除了50步首次换chunk，也不能据此保证抓取成功。阶段固定、不跨新chunk滑动延长。沿用首次30步和两项等待开关，新增这一项进行同任务比较。104项相关CPU测试、旧记录审计和单任务dry-run通过，GPU闭环待测。

## 阶段内去重（2026-10-31）

新增`--critical-wait-phases`，必须同时带`--critical-wait`。借鉴本地PACE论文3.2/3.3节的运动曲线平滑、显著低谷及阶段边界，复用key_phases中的XYZ指令范数/三点中位数/峰谷提取。PACE本身选择执行边界；这里的“同一阶段最多一次等待”是项目扩展，不是论文原公式，也未做演示数据阈值标定。

第一次等待完成后，记住旧预测中该关键动作所属阶段及其固定结束位置。该位置前的后续触发不再强制等待，但新推理仍按原M3规则进行。阶段结束或相反夹爪事件允许新等待。新预测不延长已记录的结束位置；未观察到下一运动峰时不建立阶段豁免，避免覆盖整段H50。

原Object0固定历史回放：保留52/138步等待，排除56/139步重复等待；后两次原耗时共0.809秒。这只是旧轨迹上的规则核验，不能据此声称新闭环少等0.809秒或成功率提升。见M3_PHASE_WAIT_REPLAY_20261031.json。101项相关CPU测试通过，单任务配置dry-run通过，待GPU闭环。

2026-10-31，用户授权实验。开关`--critical-wait`，仅支持M3，默认关闭，Fast不启用。基于当前机制一已经选中的action_event刷新，不更改阈值或增添关键事件。

原有异步照常运行。若新推理仍未提交，执行步抵达该次请求记录的critical_step，则在执行这一动作之前暂停仿真；轮询原有harvest及请求看门狗，直到该次结果提交。推理不取消、不重算。暂停期间不调用env.step、不消费队列、不增加执行步；RTC提交按真实执行位置截取新动作，延迟队列也记录真实执行步数。它不改变已启动推理时使用的前缀估计。

每次等待记录critical_wait trace事件和请求字段；episode输出critical_wait_count及critical_wait_seconds。等待计入整任务真实耗时与能量，控制周期估计扣除显式等待，避免将暂停解释成执行变慢。

这是仿真内的暂停实验；真实机械臂的保持控制需另行实现。事件触发之前就已执行过的关键动作无法补救，也不假定等待必然提高成功率。
