# RTC初始延迟敏感性小实验

对象：LIBERO10 task3（黑碗入下层抽屉并关抽屉）。本实验回答成功是否依赖初始延迟恰好为9，不用于挑选最好参数后改写正式结果。

## 设置

- RTC初始历史8、9、10、11步各3回合；另加3回合关闭引导对照，共15回合。
- 初始值只用于创建delay历史，之后按实际执行更新；不是全程固定delay，也不改变H/N。
- 组序交错：第一轮8/9/10/11/无引导，后两轮轮换起点。相同seed7/init0，是相同场景下的真实异步重复性，不是15个独立任务或泛化评测。
- 高频Full＋原Continue降频，H50/N5/BF16/state、完整双视角、关键等待/阶段去重/首次无事件30步均固定；不加入Fast、低频Full或新动作融合。
- 模型、专家、单任务环境和图准备复用，一次加载。每回合重新初始化队列、调度、随机种子及环境初始状态。

“无引导”使用同一FlashRT感知和同一OpenPI专家，但每次生成时不传旧动作目标，走torch.no_grad的普通5步流匹配，不求VJP。保持既有异步调度与按实际步数裁剪；初始供给估计固定9，后续正常更新。这不是更换FlashRT原生专家的速度基准；运行时间变化也会影响真实异步输入，比较时一并记录。

## 输出

rtc_sensitivity.csv/json列出各回合成功、完成步数、时间及断供。保留请求级实际delay、初始观测/噪声/动作一致性、提交步号和原始控制记录。15份初始预测互相核对，不以“seed固定”代替输入检查。独立审核对关闭引导组明确要求无旧目标、guidance=false且VJP为空。

判读：若仅个别初值成功，说明该闭环有明显参数敏感性；若同一初值重复成败不同，还存在异步时序敏感性。若无引导也频繁失败，再检查模型/任务本身；即便如此，也不能仅凭此单任务证明过拟合。

## 执行

在已有tmux终端：

```bash
bash scripts/run_m4_ssh.sh --acceptance-group m3 --task-indices 10 \
  --rtc-delay-sensitivity --critical-wait --critical-wait-phases \
  --first-refresh-step 30 --phase-refresh
```

命令dry-run已确认15回合、一次模型加载、Full高频、Fast关闭。真实启动需用户终端sudo密码；未取得GPU实测结果前不宣称任何一档更好。原默认路径不启用此实验。
