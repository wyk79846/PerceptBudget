## 本次改进重点

先把关键操作看成一段阶段，而不只一个夹爪切换点。目标是区分接近、对齐、抓取/释放及重新平稳移动；不是仅凭夹爪闭合就整段禁止Fast，也不是见到每个小谷底都增加刷新。

1. 先在已有成功与失败日志画出预测指令幅度、显著谷底、夹爪/转向事件及实际Full/Fast交接，检查是否漏掉接近布丁与夹持稳定阶段。真实物体/接触及子目标只用于离线核查，不偷用作线上输入。
2. 以显著低速区域两侧的减速/恢复运动为阶段边界候选，结合现有夹爪/转向预测确认；先只记录候选保护区，不改刷新时刻或增加模型调用。具体边界参数须用日志核查，不预先宣称可靠。
3. 候选确实覆盖此前漏判且不过度覆盖普通搬运后，再单独接入Full/Fast准入：关键阶段优先Full，其他候选仍按既定服务时限与成本选择。初次只改变准入，不同时改q、RTC、调频和模型，便于归因。
4. 闭环先选同一失败任务及一个已成功短任务，保留旧320动态版本与q5交替参考，不由一例成功就宣称普遍改善。

本轮仅恢复候选与离线核查，未部署新关键阶段规则，也未启动新GPU闭环。

## 实验版实现（2026-10-31）

`key_phases.py`在每次提交时提取一次区间：XYZ指令范数→3点中位数→相邻运动峰之间的显著低谷→用现有夹爪开合/转向事件确认。显著性沿用现有minimum_motion与slowdown_ratio；区间起于减速前的运动峰，止于下一运动峰。若预测内还看不到恢复，则止于本chunk末尾；不是固定前后各若干步，也不是识别物体或真实速度。上述具体实现为工程候选，尚无训练演示阈值标定。

`--fast-key-phases`仅用于320的V4候选：选择器逐个候选计算其计划开始时刻，检查从获取Fast观测到最大动作覆盖结束的区间，是否与当前chunk关键区间相交。包含感知/在途，是因为关键阶段取到的简化观测也会影响后续动作。未来Fast尚未生成，因此动态调度以既有H50覆盖上界作初始保守检查；不据此延长动作可靠范围。Full的deadline及启动公式不变，无新增谷底刷新触发；Full/Fast仍高频、Continue低频。

区间绑定当前已提交预测编号，下一chunk重算，不继承旧区间。恢复期间若新的检查已禁止待启动Fast，则取消该待启动选择、下tick重新规划Full；不打断已经启动的推理。原版机制一/RTC/频率工具和默认运行入口不改。独立审计重算候选覆盖区间和相交判定，并绑定来源chunk；区间特征本身通过同一提取函数核对及人工样例测试，不声称独立验证其语义正确性。

离线结果：M4/20261030T221420.704730Z-key-phase-offline-5f27343c。旧320 Long6六次Fast中五次被候选规则拒绝；416失败记录七次中四次拒绝，其中61、125、189步可被识别。旧q5成功参考Spatial/Object/Goal分别拒绝4/6、5/9、0/7；q5覆盖预测按max(q,估计Fast延迟)+此前Full延迟+一tick，不误用50步。它们只是固定历史上的决策对照，不是新成功率或最终Fast比例；可见规则偏保守，闭环后再判断代价。

81项相关CPU测试通过，覆盖信号边界、跨区间、Full时刻不变、区间替换及恢复撤销。50步检测本机CPU500次中位0.846ms、P95 0.859ms，每提交一次计算，不新增模型调用。新GPU闭环尚未执行，先Long6一次；不恢复416、30步限制或夹爪状态门槛。

## 修正：关键区间接回Full启动时间

首次准入闭环76cafa67正常运行但Long6超时；102步Fast在110步提交，新预测已标出105–144关键区间，却仍到140步才Full、151步提交。原因是首版仅改Fast准入，未使用当前Fast区间推进Full的截止时刻。

当前Fast有未结束关键区间时，选最早区间：未开始，给既有timing_plan加入区间开始这个硬期限；已进入，把响应期限设为当前时刻，让Full尽快请求。仍只扣一次完整Full服务时间和eta，RTC提交上限等硬界继续生效。这里不使用原“事件点在已承诺执行窗内就忽略”的过滤，区间是独立响应义务。

只有当前chunk为Fast时建立此义务；Full提交后当前chunk变为Full，立即解除，不会因为同一谷底再次要求紧急Full。记录source prediction、区间、目标步、active/upcoming状态及Full提交完成时间。正在运行的推理不被打断。

147项相关测试通过（包含既有时限/余量回归）：复现110步缺口、未来边界、预算只扣一次、Full/过期区间不触发、Full提交解除和latest信号策略硬期限；另保留原检测/准入/时钟/审计测试。用093c2eba的真实Fast提交前历史进行CPU调度重放，新版本在110步start_now=True、选择Full，旧版仍等待buffer；结果存该run/full_phase_response_replay.json。重放不等于新轨迹或成功率。
