## 一、目标和本阶段范围

把M1的动作执行记录和M2的设备测量接入真实异步运行，形成下面的闭环：

**读取未来动作提示和剩余缓冲 → 确定新动作到达时限 → 算出最晚启动时间 → 决定是否降频Continue → 提前恢复并Full刷新 → RTC衔接 → 用实际结果更新下一次决策。**

本阶段先用Full和Continue。Full使用完整双视角与state，生成新动作；Continue执行已有动作。继续采用当前模型、H=50、N=5、BF16和完整RTC。一次刷新内，感知上下文与动作专家串行运行；控制线程同时执行旧动作。

按10月28日直接对照和用户确认，当前M3使用原版机制一选择刷新时机。夹爪切换、减速和转向参与主线；去噪触发、混合取早及邻近事件合并保留作对照，不默认启用。机制一进一步优化后置。M4再扩展动态Fast选择和完整设备配置搜索。

最终回答三个工程问题：何时需要新动作，何时开始准备设备，以及等待期间怎样省电。交付真实任务中的能耗、质量和供给记录。

## 三、运行时如何判断

### 3.1 先读清动作和实际执行位置

每份chunk保留预测编号、观测时间、动作起始索引、原始动作及实际控制动作。每个控制周期读取当前执行索引、尚未执行的连续区间和实际设备频率。

新chunk提交时，沿用RTC的对齐方式，扣除推理期间已经过去的部分。队列中的动作按绝对执行索引使用一次，已经执行或过期的动作从计数中移除。物理执行时间从控制日志更新，不固定按“剩余步数×50ms”估算全部墙钟时间。

H=50提供预测范围。有效使用范围还需要结合M1中的质量记录、最大观测年龄和接下来识别的关键操作确定。动作提示负责提前刷新，不负责把全部预测尾段自动认证为可靠。初始最大使用范围和观测年龄从M1已有曲线及轨迹中选取，在校准任务上核对后写入配置；没有事件时仍按这两个限制启动刷新。

### 3.2 当前启用原版机制一

使用已经反归一化的LIBERO七维控制命令，读取当前chunk中尚未执行的动作。这里的平移幅度是控制命令范数，不是真实末端速度，提示也不等于检测到物理接触。

|提示|当前实现|
|---|---|
|夹爪切换|开合命令跨过±0.2阈值，连续2步确认切换|
|减速|前一步平移命令幅度至少0.1，后续连续2步不超过前一步的50%|
|转向|平移幅度不小于0.1，后续连续2步方向相对前一步改变至少60度|

当前转向提示只计算XYZ平移方向，旋转命令保留记录，没有额外独立旋转触发器。事件按chunk来源和绝对执行索引标识；已经执行的提示移除，保留原来的同类事件匹配与覆盖处理。每次新预测提交后重新提取，在当前有效区间内取最近提示作为关键操作边界。

初始参数在本轮正式比较中固定，三组B/C/D一致，不增加合并、谷底、延长确认等实验规则。state和接触记录用于核对动作表现；额外的执行偏差触发仍是后续扩展，不冒充已上线功能。

去噪波动保留作消融：它读取5步去噪中的干净动作估计，在7维上计算方差，以此前5次预测的均值加2倍标准差选边界。此前纯去噪与混合结果分别保留，不在当前正式方案中参与刷新。关闭的是去噪触发信号，模型仍正常执行N=5去噪生成动作。

### 3.3 计算新动作最晚何时到达

当前主线使用机制一和缓冲两个时限，未标定的固定2秒观测门槛关闭；年龄检查保留为可选历史设置。

- 关键操作时限：最近的未来夹爪、减速或转向提示预计到达时刻。
- 缓冲时限：当前有效动作区间预计耗尽的时刻。
- 观测时限：只在实验明确启用年龄检查时参与。

**新动作到达截止时间＝当前启用时限中最早的一个。**

没有事件时使用有限缓冲边界，不能把H=50之后的动作继续算入供给。事件已经很近或来不及时立即申请刷新，并记录预计与实际迟到。每个控制周期使用实际推进速度更新预计时间，RTC提交可行性仍另外约束最晚启动。

### 3.4 用M2数据计算最晚启动

沿用Word公式，并加入观测年龄检查：

**最晚启动时刻＝新动作到达截止时间－当前路径的完整服务时间估计－额外时间余量。**

完整服务从设备准备开始算到新动作可以提交，包含调频恢复、取得新观测、预处理、上下文、专家、RTC和提交。M2表中的恢复耗时已经在内，计算时只扣一次。

第一版按路径分别维护高频热运行、高频恢复后刷新的服务记录。先读取M2对应请求，用较高分位数作为初始估计；启动试跑可用经验95分位，并从50ms额外余量起步。校准时根据实际迟到和控制周期调整，冻结后进入比较。在线记录按同一完整边界更新，持续较慢时及时增加估计。

静态M2数据用于热路径启动；恢复路径同时载入已审核M3三任务的12条真实异步恢复样本，初始95分位634.373ms，50ms余量不变。后续真实并发样本继续更新。每次保留采用的样本来源、分位数、估计值及实际耗时，直接分析预计和实际差多少。200ms、1s是已有测量点，其他空档先采用相邻测量中较大的服务估计，再用实际运行记录补充。

**当前可等待时间＝最晚启动时刻－当前时刻。**

这是本次能继续不推理的最长时间。每个控制周期根据动作推进和新事件重算；达到启动时刻即开始设备准备。

### 3.5 决定Continue期间是否降频

第一版比较两条路径：

| 路径 | 做法 |
|---|---|
| 保持高频 | Continue期间维持高频，到对应最晚启动时刻直接Full |
| 降频后恢复 | Continue期间降低GPU和EMC频率，到对应最晚启动时刻恢复高频并Full |

两条路径分别计算服务时间和启动时刻。降频路径还需满足：

**预计低频等待节省的能量＞进入与退出低频的额外能量。**

沿用M2已完成的高低频配对测量作为初始依据。第一版可从约200ms以上的空档尝试降频，结合预计净收益判断；1s用于较长空档的成本参考。运行时等待多久由在线计算决定。Continue可以高频，也可以低频。

恢复频率时机器人继续执行已有动作。控制线程保持当前CPU频率和响应能力；推理已经启动后，高频保持到本次刷新完成。

### 3.6 提交结果，进入下一轮

Full启动时冻结一次新观测快照。当前只运行一个刷新；已有刷新时，新事件更新下一次需求和截止时间，至多保留一个可替换的待执行请求。待请求真正启动时再取得新快照。

RTC还要求新推理提交时满足`s+d≤H`：s为旧chunk已消费步数，d为同一DelayQueue预测的推理消费步数。调度同时计算最晚提交步`origin+H−d`，低频恢复保留下一控制周期确认和现有时间余量，避免等待升频时跨过可用前缀。与墙钟启动约束取更早者。

RTC继续按实际执行进度衔接新旧chunk。保留当前经过验证的延迟估计和前缀约束，核查动态触发是否满足其调用要求；若某次无法满足，记录冲突并按既定回退处理。服务完成后更新动作队列、事件位置和服务统计，开始下一轮判断。

频率助手复用M2的设置、核验与恢复函数，任务级控制使用有界握手，按在线请求升降频。M2固定五次请求和定时回放属于标定流程，不直接拿来控制真实任务。任务结束、通信断开或超时后恢复原设置。

实现一条统一状态流程即可：

**Continue／计划刷新 → 降频等待（若选择）→ 恢复 → Full计算 → 提交 → Continue。**

## 四、故障处理与正确性检查

看门狗与调度使用同一单调时钟。控制线程检查动作队列、在途请求和设备准备进度，异常处理不依赖推理线程自行返回；外层普通用户监控进程负责终止无返回的工作进程，调频助手独立完成有界恢复。

| 情况 | 处理与记录 |
|---|---|
| 关键操作突然提前、state偏差增大 | 更新截止时间，取消尚未执行的等待计划，尽快恢复并请求Full |
| 设备恢复或推理迟到 | 保持已有有效动作的正常消费，记录预计/实际差和违约时间；后续提高对应服务估计 |
| 当前索引没有有效动作 | 进入统一的欠载动作，记录连续事件和持续时间；恢复供给后按实际索引衔接 |
| 推理卡住或返回异常数据 | 到达请求超时即停止提交该请求的结果，完成运行退出和调频恢复；保留原因及已发生能耗 |
| 用户中止、内存保护触发 | 复用现有退出、GPU锁和有限时长调频恢复流程，核验恢复记录 |

欠载动作在所有比较组中一致，首次接入时明确并固定机械臂保持和夹爪命令。日志将正常Continue与欠载处理分开统计。

先用不加载模型的可控时间测试覆盖：短/长空档、无事件、立即事件、重复事件、实际周期变化、过期动作、在途请求和迟到。随后在实机上分别注入一次额外推理延迟、推理无返回、动作缓冲耗尽，核对看门狗、动作索引与频率恢复。这些用短窗口完成。

## 六、统一结果口径

M3统一统计同任务的实际模块输入能量，不减静态等待或Continue基线。

| 指标 | 计算与报告方式 |
|---|---|
| 每次尝试总能量，J | 积分该次任务全部VDD_IN记录，覆盖首次推理、控制、监视、等待、调频和废弃计算 |
| 每成功任务能量，J/成功任务 | 全部成功、失败、超时尝试的总能量÷成功次数 |
| 成功率 | 成功次数÷尝试次数，并给出逐任务配对结果 |
| 完成时间 | 同时列真实墙钟时间和实际执行步数；成功、失败、超时分别汇总 |
| 平均功率，W | 任务总能量÷同一积分窗口时长 |
| 每执行步能量，J/步 | 作为辅助指标，使用任务总能量÷实际执行步数 |
| 欠载 | 控制周期比例、连续事件次数、每次时长、总时长及发生阶段 |
| 调度效果 | 关键操作提前量、预计/实际服务耗时、迟到、观测年龄、频率和触发原因 |

## 10月28日补充：看门狗短窗口验证
