# M4低频Full复核（2026-11-02）

本轮只读源码、复算已有原始数据、运行CPU检查；没有启动GPU实验，也没有更改调度。

## 已定位的问题

此前把截止到结果ready的短服务窗口，作为低频Full是否节能的依据，不成立：高低频时长不同，终态和功率读数尾段未统一。不能把短窗高7.708J、低8.185J直接解释为低频路线更耗电。这是结论和计量边界的问题，尚不能归因为某一调频代码错误。

已有同输入、同噪声、LOW起终态、共同4秒的10对直接实测：高频路线34.43897J，低频路线31.28471J，低频少3.15427J/9.159%。高频服务507.30ms、低频701.88ms；全部20次动作输出一致，功率覆盖完整、频率及恢复通过。本次从route_power_block原始采样独立梯形积分复算，而非只读取summary，结果一致。

4秒结果含等待尾段，不能改称单次Full纯计算能量，也不能外推整任务省9.16%。

## 调度代码核查

- m3_low_full.LowFullRuntime仅在已确认LOW、没有待完成调频时准入低频Full；计算期间不升频。
- 关键阶段或低频赶不上时，回到原高频恢复流程；已有恢复计划时不反复准入低频。
- 截止时间沿用关键事件/缓冲界限；低频服务较长，因此减少此前Continue等待、提前启动。未新增固定交接，结果就绪即RTC提交。
- 高低频使用各自RTC延迟队列，低频服务样本不混入高频预算。
- 选择遵循“普通阶段低频赶得上就用”，不使用旧能量估计决定准入。choose中的energy_j为历史成本模型诊断，不能作为本次实际耗能。
- 现有9项低频Full CPU检查全部通过，覆盖关键/迟到回退、频率保持、服务历史隔离及最后可行控制周期启动。

没有发现当前实现会在一次低频Full内重复升降频的证据。不能据此保证整个闭环无其他问题；当前12任务扩测仅完成2项，另10项未测。
