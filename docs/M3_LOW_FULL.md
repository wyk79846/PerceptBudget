# M3低频Full：完整剩余窗口调度（2026-11-01）

当前策略shared_deadline_v4。以11/12版本M3为对照，保留关键点、阶段等待/刷新去重；Fast关闭。不新增区间入口交接或固定交接位置，不缓存已完成结果等待人为交接点。

## 运行流程

1. 当前预测完成后，按原RTC方式立即接续；剩余动作按新预测的观测origin计数，例如30步取观测、40步提交，H50仍剩40步，覆盖到80步。
2. 用剩余有效动作及未覆盖关键点确定下一次最晚算完时间，沿用原M3判断。
3. 从完整剩余窗口安排Continue＋推理：高频完整预算较短，可以多等；低频预算较长，就少等。两者共享原关键点/缓冲截止，且只扣一次25ms余量。低频普通阶段赶得上就选，不按能量筛选；首次和关键阶段保持高频。
4. 同时保留RTC真实的有限重叠约束H−executed≥delay，但不再将高频9—10步的延迟估计当成整个可用时间上限。每档delay按自己的历史估计，低频的delay也不挤占高频边界。
5. 低频RTC初始delay用已有低频实测中位推理耗时÷当前环境实测控制周期换算，与高频初始化方式一致，不再用固定50ms和服务预算硬算16步。后续分别观测实际执行步数。
6. 结果完成即由原harvest提交，再判断下一次刷新。推理期间不切频；赶不上则启动前恢复高频，关键点仍保留等待兜底。

频率不同可能需要不同的请求时刻和RTC延迟估计，因此不承诺预测或独立闭环轨迹逐项一致。保留的是关键判断、阶段去重和截止计算，而不是固定观测时刻。此前关于“同输入同交接必然相同”的讨论描述了另一种固定交接协议，不是当前运行方式。
